# CastFabric 从产品设计到实现的阶段路线

## 总原则

每个阶段必须有独立产物和明确验收门槛。未通过当前阶段，不修改下一阶段对应的生产
代码，不部署到 Home Server，也不以“先试试看”为由混合产品决策与技术实现。

## P0：恢复边界与持久化产品事实

**目标：** 修正上下文错位，形成唯一有效的品牌和多音响模型。

**产物：**

- CastFabric 品牌与端口—适配器 ADR；
- 每音响独立 Receiver Suite ADR；
- 修正后的系统架构与产品设计文档；
- 被取代的旧 UI 方案明确标记为 Superseded；
- 提前进入实现的工作以可恢复 stash 封存。

**通过条件：** 文档中不再把 MiAir 当项目名，不再把 MiPlay 当产品名，不再存在全局
单选音响的有效设计。

## P1：控制台产品原型

**目标：** 用真实信息层级验证产品，而不是验证 CSS 风格。

**范围：** 总览、音响、活动、连接配置、中英文、桌面与移动端；使用固定演示数据，
不连接生产 API。

**通过条件：**

- 多台音响同时出现，启停语义不存在互斥误解；
- 首页能区分正在播放、等待投放、需留意和已停用；
- 活动记录明确关联音响；
- 配置不挤占首页；
- 用户完成视觉和产品逻辑确认。

## P2：异常状态与完整交互原型

**目标：** 补齐正常截图之外真正影响实现的数据和状态。

**范围：** 首次发现、空列表、扫描中、部分音响离线、单协议降级、端口冲突、会话
接管、不同音响并行播放、重连、扩展失效、加载/错误/空状态与键盘路径。

**通过条件：** 每个状态都有用户可理解的文案、下一步动作和稳定的数据归属，不依赖
开发者查看日志才能解释。

## P3：技术设计重写

**目标：** 根据已确认产品模型重写 API、配置、服务实例和迁移方案。

**必须明确：**

- `ReceiverSuite`、`OutputTarget`、`MediaSession` 的职责与生命周期；
- 多实例 mDNS/SSDP 标识、端口分配和冲突处理；
- 集合式 API 与事件模型；
- 旧单目标配置如何迁移为首个启用音响；
- 多音响并行时的资源上限和故障隔离；
- 无账号、无音箱、无手机时的离线验证方式。

**通过条件：** 新实施计划逐任务列出测试、迁移、回滚和提交边界，并由用户明确授权
进入实现。

## P4：分层实现

建议顺序：领域模型与测试 → 目标发现/持久化 → 每音响 Receiver Suite → API → Web UI
→ 兼容迁移 → Docker/CI → Home Server。每层均在单独提交中通过测试，不提前部署。

## P5：Home Server 与真机验收

先验证部署健康、发现广播和实体 DLNA，再依次验证虚拟 DLNA、AirPlay、MiPlay 的发现、
播放、暂停、音量、接管和延迟。认证失效测试必须证明标准 DLNA 核心不受小米扩展影响。

- P4：完成；每音响 Receiver Suite、多目标 MiPlay、安全 API 和生产控制台已分层实现，
  148 项测试与 Docker CI 通过。
